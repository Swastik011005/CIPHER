# Known limitations and what was (not) measured

This page lists, without softening, what the project does not do and which claims rest on measurements. Use it when answering
"what did you not build?" in the viva.

## 1. Nature of the project
- **Everything is a simulation.** Traffic is synthetic and generated by the engine. Nothing is captured from, sent to, or blocked on a real network. "Blocking" changes state inside the simulation.
- **No real device behaviour is claimed.** The firewall, ACL, IDS and IPS are our own models of the concepts, written to follow the rules in `docs/SECURITY_ENGINE.md`. They are not Cisco IOS, Snort, Suricata or any real product, and no configuration here can be loaded onto one.
- **Detection is rule-based and threshold-based.** There is no machine learning and no signature database.
- Packet timing in the 3D scene is a visual schedule; it is not a latency model of real hardware.

## 2. Not implemented (planned in the early plan, cut or never started)
| Item | Status |
|---|---|
| Cisco Packet Tracer lab (`packet-tracer/`) | **Not built.** Only a feature-check note exists. There is no `.pkt` file, no test matrix T1 to T12 and no parity table. Nothing in the app or the slides claims Packet Tracer results. |
| D3 half-open connection condition | Not implemented. D3 counts connection-starting packets per second only (more than 25 per second over 5 s is MEDIUM, more than 50 is HIGH). |
| D7 host-sweep detector | Not implemented (listed as future work). |
| Monitoring-page charts (traffic over time, protocol doughnut, top talkers) | **Built** (Chart.js, `frontend/src/features/monitoring/MonitoringCharts.jsx`): a stacked traffic chart with the playhead, a protocol mix and the busiest senders, all counted from the loaded trace. |
| PCAP export and hex dump of packets | Not implemented. |
| Follow-packet camera | Not implemented. |
| Syslog packets travelling to SEC-LOG | Not built. IDS-1 and IPS-1 alerts are shown in the UI, but no syslog packet is simulated (the event type exists in the schema and statistics, the engine does not emit it). |
| Editing rules *during* a run | Rule edits apply to the next run. Mid-run, the controls (IPS mode, detector on/off) and custom traffic re-simulate from the playhead; thresholds and restricted addresses cannot change mid-run. |
| Persistence of edited rules | Edited rules live in the backend's memory only and are gone when it restarts (Reset to shipped restores the defaults). |
| Editing the IPS action table, the allowlist, the firewall rules or the core ACL | Shown, not editable, because they are the design. What is editable: each detector's switch and numeric settings (within validated limits) and the restricted outside addresses. The firewall/ACL tables can be exported as Cisco IOS text (export only; it was not loaded on any device). |
| Run history / database | Runs are kept in memory only. |
| NAT, IPv6, real routing protocols, wireless | Out of scope. Routing is static. |
| Light theme, mobile layout | Not built. The UI targets desktop widths. `scripts/check_app_audit.mjs` checks that no page scrolls sideways at 1920, 1440, 1366 and 1024 px; at 768 px the pages still fit, and at phone width (390 px) they scroll sideways. Browsers tried: Chrome and Edge. Firefox and Safari were not tested. |

## 3. Performance: what was measured and what was not
Measured on the development laptop in a real Chrome window, S4 (heaviest scenario) at its peak, using `scripts/measure_fps.mjs`:

| Window size | Quality | Frames per second |
|---|---|---|
| 1350 x 673 | Low | 59.3 |
| 1424 x 805 | Low | 59.2 |
| 1904 x 985 | Low | 31.1 |
| 1350 x 673 | High | 31.3 |
| 1424 x 805 | High | 27.2 |
| 1904 x 985 | High | 15.2 |

These were measured on the **Intel UHD integrated GPU**. The acceptance target "30 frames per second on Low on an integrated GPU" is met at all three sizes. Memory: a 10-minute S4 run changed the JS heap by **-1.2 %** (target: under +15 %), raw data in `docs/perf/memory-s4-high-10min.json`.

**The discrete-GPU target is NOT verified.** The plan set a target of 55 frames per second on the High preset on an RTX 4050. During the earlier measurements Windows did not detect the RTX 4050 (the device reported `Present = False`). On 3 November 2026, during Stage 7, Windows did list it as present (`Present = True`, `nvidia-smi` sees it), but a measurement with the default Chrome settings still rendered on the **Intel UHD** GPU (the WebGL renderer string said so): S4 peak, High, 1904 x 985, **17.8 fps**, consistent with the earlier 15.2. Making Chrome use the RTX needs a Windows per-app graphics preference for Chrome (Settings, System, Display, Graphics, High performance), which is a system setting we did not change. **We do not claim the 55 fps RTX target has passed.** To test it: set that preference, restart Chrome, run `node scripts/measure_fps.mjs --scenario S4 --mode enforce --start 12 --seconds 10 --quality high --url "http://127.0.0.1:8000/simulation?debug=1"`, and check that the `gpu` line in the output names the NVIDIA GPU before trusting the number. Until then the High preset is demonstrated only as "looks right, runs at 15 to 31 fps on integrated graphics"; use **Low** on that laptop.

## 4. Verification limits
- The automated tests (backend pytest, frontend Vitest, the 93 scenario checks) prove the engine and UI logic. The real-browser rehearsal (`scripts/rehearse_demo.mjs`, 34 checks) proves the expected on-screen numbers in `docs/DEMO_SCRIPT.md` in Chrome. Neither proves the **look** of the 3D scene on other GPUs or in other browsers; only Chrome on the development laptop was used.
- The 9:40 narration timing of the demo is a plan. The rehearsal script checks results, not how long a person takes to speak.
- **The fresh-clone install was tested on one machine** (the development laptop, with caches emptied). The second team laptop was **not available**, so installation there is untested. Differences between the two machines are therefore unknown; see `docs/STAGE7_PROGRESS.md` for the one machine's environment.
- **No screen recording was made** by the agent that prepared this release. `docs/BACKUP_AND_RECOVERY.md` explains how the team makes one; until the team records it, the backup is the set of screenshots in `docs/demo/` and `docs/screenshots/`.
- The app has no automated accessibility audit beyond the checks that exist in the frontend tests.

## 5. Security of the app itself
By default the backend binds only to loopback addresses and refuses anything else. There is no authentication, by design. A public deployment must opt in explicitly (`NETSEC_ENV=production` plus `NETSEC_ALLOW_PUBLIC_BIND=true`) and then runs with read-only rules, rate limits and a request size limit (`docs/DEPLOYMENT_RENDER.md`). In a local run the Rules API still accepts edits from any local process. The rule store and the rate limiter are in memory in one process, so a deployment must be a single instance; per-visitor rules would need a redesign (sketched in the deployment guide, not built).
